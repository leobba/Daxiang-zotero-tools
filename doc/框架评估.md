## 0.0 实施结果（本报告结论已全部落地）

四个决策已确认并实施完毕：插件命名 **MyZoteroTools**、toolkit 走 **6.0.0 模块化**路线、
功能 3 降级为提示条中的聚合数量、用**真实库**验证。

| 验收项 | 命令 | 结果 |
|---|---|---|
| 构建 + 类型检查 | `npm run build` | ✅ 通过，产出 **18,847 字节** `my-zotero-tools.xpi` |
| 代码规范 | `npx eslint src test` | ✅ 0 问题 |
| 行为测试（真实库） | `npx zotero-plugin test --no-watch` | ✅ **8 / 8 全部通过** |

行为测试里最关键的两条：

- ✅ **插件结果与 Zotero 自带全局递归逐条一致**——证明「按需智能递归」忠实复现了 Zotero 的递归语义；
- ✅ **聚合后用户看到的顶层条目数 = 子分类条目并集**——证明最终列表内容正确。

实现阶段新发现的三个问题（本报告写作时未知）：

1. **`collectionID` 是快捷条件，存储时会规范化为 `collection`**
   （`searchConditions.js:271` 的 `noLoad: true` → `:295` 的标准条件）。
   一开始按 `collectionID` 匹配导致注入始终不生效，靠打印 scope 链才定位到。
2. **`search()` 的返回条数大于分类内条目数**：分类场景下 `_scopeIncludeChildren = true`
   （`search.js:641-652`），会额外纳入作用域内条目的附件/笔记/批注。
   这是 Zotero 原生行为，不是缺陷；因此测试基准改为「与自带递归对比」而非自行推算。
3. **`zotero-plugin test` 每次清空测试数据目录**，无法用环境变量指定。
   已用脚手架提供的 `test:init` 钩子解决（见 `zotero-plugin.config.ts` 的 `seedTestDatabase()`）。

## 3. 方案 A 详解（基于实拉取的 49 文件模板）

模板 `main` 分支 `306d4e2a`；**最新 release v3.1.0 发布于 2025-03-29**——相对当前生态已滞后约 18 个月。这正是 §4 全部坑的来源。

**目录结构**

```
addon/                       静态资源（原样打进 xpi）
  bootstrap.js               入口：registerChrome + loadSubScript + hooks.onStartup()
  manifest.json  prefs.js
  content/{preferences.xhtml, zoteroPane.css, icons/*}
  locale/{en-US,zh-CN}/{addon,mainWindow,preferences}.ftl
src/
  index.ts  addon.ts  hooks.ts
  modules/examples.ts        ~25 KB 官方 API 示例（演示代码，非框架必需）
  modules/preferenceScript.ts
  utils/{locale,prefs,window,ztoolkit}.ts
test/startup.test.ts
typings/{global,i10n,prefs}.d.ts
zotero-plugin.config.ts
```

**生命周期**：`onStartup`（等 3 个 promise → i18n → 注册 prefs/notifier/快捷键/列/面板 → 逐窗口加载）→ `onMainWindowLoad/Unload` → `onShutdown`（`unregisterAll()` 统一清理）。
约定明确：**hooks 只做分发，业务逻辑放模块**——对长期维护友好。

**热重载（选它的最大理由，已在 `zotero-plugin-scaffold@0.9.2` 源码中核实）**
`serve` 通过 Firefox **远程调试协议（RDP）**安装并重载插件（类似 `web-ext`），改文件 → 自动重编 → 自动重载，**无需重启 Zotero**；调试输出自动落盘到 `.scaffold/logs/`。
> 注：proxy-file 方式**不支持重载**，scaffold 走的是 RDP，这点比手写方案强得多。

**i18n**：Fluent `.ftl`，构建时自动重命名并给消息 id 加前缀；**已内置中英双语**。

## 4. 四处版本断层（本次评估的核心产出）

### 断层 1：`zotero-types` 的 git 依赖 —— 直接让 `npm install` 失败

`zotero-types`（**含最新 4.1.3**）声明了两个 GitHub git 依赖：

```json
"pdfjs-dist": "github:zotero-plugin-dev/zotero-pdfjs-types#main",
"epubjs":     "github:zotero/epub.js#a6139d586b66d404f3da2b846598960c0394afc5"
```

npm 12 默认 `allow-git=none` → 报 `EALLOWGIT`，安装中止；且 `git+ssh://git@github.com` 在本机不可达。

**解决（已验证）**：
1. 用**嵌套式 override + `npm:` 别名**重定向到 npm 正规版本：
   ```json
   "overrides": {
     "zotero-types": {
       "pdfjs-dist": "npm:pdfjs-dist@5.4.624",
       "epubjs": "npm:epubjs@0.3.93"
     }
   }
   ```
   > ⚠️ 扁平写法对 `pdfjs-dist` 生效但对 `epubjs` **不生效**，必须嵌套。
2. **必须删除模板自带的 `package-lock.json`**——它把这两个包锁死为 `git+ssh://…`，导致"`--dry-run` 通过、实际安装失败"的迷惑现象。

> 调研中还发现另一条更简短的路：`npm install --allow-git=all`。但它依赖 GitHub git 通道，与本机实测不符，**不采纳**。已采用 overrides，已实测 298 个包安装成功。

### 断层 2：`zotero-plugin-toolkit` 移除了 `ZoteroToolkit`

| toolkit 版本 | 发布 | `ZoteroToolkit` |
|---|---|---|
| 5.1.0-beta.13（模板所依赖） | 2025-11-14 | ✅ |
| **5.1.4** | 2026-06-14 | ✅ |
| **5.2.0** | 2026-07-21 | ❌ 改为 23 个模块化导出 |
| 6.0.0（最新） | 2026-10-03 | ❌ 模块化 |

模板的 `^5.1.0-beta.13` 会解析到 5.2.0 → 打包报 `No matching export … "ZoteroToolkit"`。

**同时注意**：toolkit 的 `MenuManager` **已被移除**（5.1.0-beta.14 之后）。**菜单请用官方 `Zotero.MenuManager.registerMenu()`（Zotero 8+）**，不要照抄 toolkit 文档（其文档已过时仍在宣传 MenuManager）。

**两条路线**：
- **甲（0 代码改动）**：钉 `~5.1.4` —— 已验证可打包。
- **乙（现代化，推荐）**：用 6.0.0 模块化 API，按模板注释里已给出的写法自建 `MyToolkit`（`class MyToolkit extends BasicTool { UI = new UITool(this); }`）。因为演示文件本就要删（见断层 3），乙的额外成本极低，且站上当前维护线。

### 断层 3：模板演示代码与 Zotero 10 类型不兼容

`tsc --noEmit` 有 8 个报错，**全部位于 `src/modules/examples.ts`**（演示代码），例如 toolkit 类型缺 `Menu`、strict 模式下 `false | Item` 未收窄。

**解决**：删除 `src/modules/examples.ts`（对自用插件是纯冗余），并把 `hooks.ts` 里对它的调用换成我们自己的模块。这一步同时解决断层 2 的路线乙。

### 断层 4：`strict_max_version` 停留在 `8.*`

已核实 scaffold **不会**自动改写该字段（只读取），必须手改，否则 Zotero 10 拒绝加载。

## 5. Zotero 10 的破坏性变更（已逐条在 `app\omni.ja` 源码中核对）

Zotero 10 与 9 同为 Firefox 140 ESR。以下变更**直接影响本项目**：

| 变更 | 影响 |
|---|---|
| 单数 getter **改为抛异常**：`ZoteroPane.getCollectionTreeRow()` → `getCollectionTreeRows()`；`getSelectedCollection()` → `getSelectedCollections()`；`getSelectedLibraryID()` → `getSelectedLibraryIDs()` | 源码 `zoteroPane.js:2194-2201` 已核实：`_requireSingleSelection()` 会抛错。**必须用复数版本** |
| `ItemTree#collectionTreeRow` **被移除** | 改用 `ZoteroPane.itemsView.viewMode` 与 `.collectionTreeRows` |
| `ItemTree` 被拆分（`ItemTree` / `ItemTreeRow` / `CollectionViewItemTree`） | 相关内部方法位置变动 |
| 多选时插入**库表头/间隔行** | 处理行前需判断 `row.isObjectRow` |
| `Zotero.MenuManager` 的 `collectionTreeRow` 上下文**抛异常** | 用 `collectionTreeRows` |
| 检索：`fulltextWord` → `fulltextContent`；`addCondition()` 对旧 `required` 参数抛错 | 构造检索时注意 |
| 撤销/重做：`saveTx({undoAction…})` + `Zotero.UndoHistory.stageAction()` | 涉及写操作时使用 |

**关键好消息**：功能 1 的补丁点 `Zotero.CollectionTreeRow.prototype.getSearchObject`（`xpcom/collectionTreeRow.js:406`）**在 Zotero 10 中依然存在且仍是构造检索条件的唯一入口**，补丁方案有效。

**关键坏消息**：`zotero-types@4.1.3` **是写给 Zotero 8 的**——它把 `getCollectionTreeRow()` 标为返回 `CollectionTree`（在 Zotero 10 会抛），且**不含** `getCollectionTreeRows()`、`getSelectedCollections()`、`viewMode`、`collectionTreeRows`、`isObjectRow`、`UndoHistory`（后者只存在于未发布的 master）。
⇒ **对策**：在 `typings/` 下加一个本地 `.d.ts` 增补文件，为 Zotero 10 新 API 补类型。这是本项目必做的一次性工作。

## 6. 四项功能与 Zotero 10 的可行性

| # | 功能 | 官方 API | 实现方式 | 风险 |
|---|---|---|---|---|
| 1 | 按需智能递归（分类无直属条目时才聚合子分类） | ❌ | 包装 `Zotero.CollectionTreeRow.prototype.getSearchObject` | **中**（补丁点已验证存在） |
| 2 | 列表顶部提示条「来自 N 个子分类的 M 条」 | ❌ | 向条目面板注入 DOM | 低-中 |
| 3 | 分类树显示含子分类的聚合条目数 | ❌ | 需自行注入分类树 UI | **高**（建议降级） |
| 4 | 条目列表「来源子分类」列 | ✅ **官方** | `Zotero.ItemTreeManager.registerColumn()` | **低** |

### 功能 1：根因与实现要点

Zotero 构造分类检索条件处（`xpcom/collectionTreeRow.js:456-461`）：

```js
if (this.isCollection()) {
  s.addCondition('noChildren', 'true');
  s.addCondition('collectionID', 'is', this.ref.id);   // 仅直属条目
  if (Zotero.Prefs.get('recursiveCollections')) {
    s.addCondition('recursive', 'true');               // 仅当全局开关打开
  }
}
```

默认值（`defaults/preferences/zotero.js:1616`）：`pref("extensions.zotero.recursiveCollections", false);`

**⇒ 这就是"一级分类不显示文献"的根本原因：不是 bug，是默认行为。**

你库里的实际情况（通过 Zotero 本地 API 读取）：

| 一级分类 | 直属条目 | 子分类 |
|---|---|---|
| 除草剂 | **0** | 农药新活性（3） |
| 农药 | **0** | 国标（6）、响应面法（2）、载体（0） |
| 项目 | **0** | 机器学习…（1）、AI驱动…（1） |
| 机器学习 | 9 | 抗性杂草…（1） |

出问题的分类**自己一条直属文献都没有**，所以列表为空——完全符合 Zotero 语义。

**实现思路**（最小侵入）：包装 `getSearchObject`，对"无直属条目的分类"临时打开 pref 后调用原实现，`finally` 还原，**完全复用 Zotero 自身逻辑**，不复制条件拼装代码。
⚠️ 全库共 **7 处**引用该 pref，其中 `itemTree.js:992` 注册了 pref 观察者会触发刷新，实现时需验证是否引入多余刷新：
`collectionTreeRow.js:459`（主行为）、`collectionViewItemTree.js:693`、`collectionViewItemTree.js:2129`（"从分类中移除条目"语义）、`advancedSearchPane.js:362`、`reportInterface.js:71/75`、`zoteroPane.js:2623/2626`、`standalone.js:559/700`。

### 功能 3：建议降级（重要）

已核实：**Zotero 分类树完全没有条目计数显示**——`xpcom/collectionTreeRow.js` 中 `count` 关键字**零命中**；`collectionTree.js` 里的 `count` 全是选区/撤销计数。且 Zotero **未开放分类树列注册 API**（`ItemTreeManager` 只管条目列表）。

⇒ 功能 3 需在分类树上自建并维护 UI（展开/折叠/刷新/排序），成本与回归风险远高于其余三项，且撞上 Zotero 10 刚重构的内部结构。

**建议**：把"聚合数量"并入功能 2 的提示条（「共 9 条，来自 2 个子分类」），数字取自当前视图计数，**零额外成本**。确有常驻数字需求再单开一期。
